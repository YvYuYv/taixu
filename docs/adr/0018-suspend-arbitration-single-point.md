# 挂起裁决单点化：lifecycle 并集裁决，意图事件驱动

路由器（槽位失配）、生命周期命令、系统信号（Page Visibility/内存/电池）三方都能触发挂起，若各自直接调用会产生"路由要挂、系统刚恢复"的竞态。决策：**唯一裁决入口在 lifecycle 服务**；router 与系统信号只发意图事件 `app/intent:suspend` / `app/intent:resume`，lifecycle 汇总裁决——挂起条件取并集（任一来源请求即挂起），**恢复需全部条件解除**（符合最小惊讶：路由挂起的应用不会因页面可见性切换而复活）。备选引用计数方案被否：来源崩溃会泄漏计数，还需租约机制，复杂度不值。

**修订（ADR-0035）**：意图**不走全局事件**（emit 是 fire-and-forget，无法阻止恶意应用挂起他人——权限黑洞），改为 lifecycle 的服务方法 `ctx.lifecycle.requestSuspend(instanceId, reason)` / `requestResume(instanceId)`，方法内经 security 鉴权（只能操作自己的 instanceId，root/系统来源除外）。基线 §2.4 的 `app/intent:*` 事件契约随之删除。

**修订（ADR-0031）**：恢复从"全部解除"改为**分级解除**——来源分级：路由（用户显式导航意图）> 系统信号 > 手动命令；高优先级来源的恢复意图可单独解除低优先级来源的挂起，但恢复后该应用进入"压力下候选驱逐"名单（若压力持续，它是下一个 LRU 驱逐对象）。并集挂起不变。原因：用户主动切换到的页签不能是死的。
